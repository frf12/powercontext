# Token 节省：证据与统计口径

## 计入记忆生成后的成本估算

同一批 24 题的单题最高降幅均来自第 456 题，两组均通过：Token 2,301,174 → 840,186（减少 **63.49%**）；估算成本 33.52836 → 16.09925 点（减少 **51.98%**）。Token 与成本均含记忆生成，成本沿用下述缓存外推假设。

同 24 题，解题加记忆生成共 17,808,978 Token，相对对照组 26,410,221 减少 **32.57%**。成本按输入 Token 加权缓存命中率 `821,504 / 846,962 = 96.994%` 推算其余 55 条记录的 1,171,777 个输入 Token。

沿用每百万非缓存输入 100 点、缓存输入 10 点、输出 500 点的固定费率，记忆生成约 37.27503 点，加解题 352.25020 点，共 **389.52523 点**；对照组为 **460.52434 点**，估算减少 **15.42%**。点数不是货币或实际账单。

该推算假设成功前缀提取的命中率适用于普通生成，可能偏乐观。不采用这一假设时，解题加记忆生成的成本范围为 386.35531–491.81524 点，不能确认一定比对照组低。Embedding、就绪检查和其他辅助费用均不在此估算中。

## Memory额外开销与实际复用情况

MCS主模型共 **15,766,986** Token。74条记忆生成记录另有 **2,018,739输入 + 23,253输出 = 2,041,992 Token**。两项合计 **17,808,978**，比OFF主模型总量低32.57%。这是部分组件之和，不是完整系统费用对照。

另外观测到业务embedding输入：记忆召回14,737、记忆索引7,679 Token。准备、就绪检查、embedding费率，以及部分生成调用的缓存字段仍不完整，完整费用为 **unknown**，不能填0。Scope与prefix交叉核对记录不能再与Core账本累加。

24条选中MCS记录均完成了记忆收尾。解题期间观测到的**非空Memory注入为0**；题后共生成54条Atomic Memory，分布在21题。每次从空库开始，最终答复后的采集与flush不能证明帮助了已经完成的解题，下一题也不继承记忆。因此，主模型用量差异不能直接归因于Memory。

完整Memory实验提前停止，未跑完全部计划任务。invalid、hold、未完成记录不作为解题失败计分，也没有混入这批已完成样本。

## 测试配置

- 数据集：SWE-bench Pro公开v2共731题中的固定121题，来自NodeBB/NodeBB、navidrome/navidrome、tutao/tutanota；Memory表使用其中已完成的24题交集。
- Codex CLI 0.162.1，`gpt-5.6-sol`，推理强度`medium`，原题prompt一致，不放入gold patch或评分输入。
- C为PowerContext原生CodeGraph，不是外部colbymchenry/codegraph；S为显式[指导文本](steering.txt)，去除首尾空白后的SHA-256为`47335a057b37c59feb790c71531fb13fee9aa23f63611aaddcac74831b40c22f`；M为启用Memory。
- Steering要求定向搜索、限定读取、合并操作和聚焦验证；测试无法运行时允许compile/import检查，因此也会影响验证路线。OFF不包含这段指导。
- Gateway OFF保留Gateway路由并关闭M/C/S；native OFF是不经过Gateway的另一基线。本文C/S/CS/MCS均与Gateway OFF比较。
- 每个组×题×模型attempt独立使用全新DB、Scope、workspace、cache、home。技术收尾恢复沿用原attempt，不为补评分或flush重跑已成功的主模型。
- 宿主记忆、插件、web search关闭，隐私检查关闭。资源为2CPU、6GiB、512 PIDs，每题限时2400秒。
- 冻结开发构建：基础commit `28ba11dc26865b4bae1bd6d9bb483248886c4c74`，移植上游修复`566834839821d026db1c116425ee9a9b5c0f4fe5`。源码、补丁、数据集与二进制摘要见[results.json](results.json)。不能把本次结果解释为PyPI默认配置或后续检索修复版本的效果。
- OFF来自较早的冻结运行，不是同时随机A/B；模型采样和共享基础设施都可能影响结果。

## 离线核算

仓库根目录下，使用Python 3：

```bash
python3 docs/benchmarks/token-savings/verify.py
```

脚本使用[results.json](results.json)检查题目对齐、用量算术、条件选择和公开总量，不调用API、不启动Agent、不运行评分。主模型用量来自CLI `turn.completed`：总量=输入+输出，缓存已含于输入，reasoning已含于输出。

导出包含五组原始121题记录、S/CS/Gateway的复跑选中与额外尝试，以及24条MCS选中记录。来源报告提供outcome摘要的记录保留该摘要。完整prompt、原始轨迹、凭据、本机路径未打包进来。来源hash用于定位证据，不等于原始轨迹已经公开；数值核算不等于独立复现评分。


## 配置与结果解读

详细数据中的缩写：**C = 代码检索（CodeGraph），S = 工作指导（Steering），M = 记忆（Memory）**；组合字母表示同时开启这些功能。**Gateway OFF** 是关闭三项功能的网关对照组。

- 同样的 24 题，只开工作指导节省 27.12%（通过 15 题）；加上代码检索节省 33.06%（通过 15 题）；三项都开启节省 40.30%（通过 16 题）。对照组通过 16 题。这 24 题是各组已完成任务的交集，不是随机抽样。
- 记忆生成另用了 2,041,992 Token。计入后，总量为 17,808,978，比对照组的解题用量少 32.57%，但仍未包含全部辅助请求。记忆生成会尝试复用网关的前缀缓存；它是独立请求，不在 Codex 的解题用量中。前缀请求与 Core 记录按同一次调用计算，不能重复相加。
- 每次运行都从新库开始。解题期间没有观察到非空记忆注入，因此不能把这次节省解释成“记忆帮助了解题”。
- 完整 121 题中，只开代码检索反而多用 10.53% Token；代码检索加工作指导比对照组少通过 1 题。模型选择的实现和验证方法也会影响用量，不能保证每道题都节省。
- 首屏采用原始运行记录，计入记忆生成，没有混入后续复跑。复跑选中的记录、全部尝试的开销，以及缓存和非缓存用量，见详细报告。三项都开启的组没有跑完 121 题。
- 测试使用 Codex CLI 0.162.1、GPT-5.6 Sol medium 和固定版本的开发构建。工作指导是测试时显式提供的文本，安装后不会默认开启。对照组来自较早的测试批次。

## 40.30% 与 32.57% 的区别

40.30% 仅统计解题主模型：15,766,986 Token。加上记忆生成的 2,041,992 Token 后，合计 17,808,978 Token，对比同一 Gateway OFF 的 26,410,221 Token，减少 32.57%。首页动图先展示仅解题开销，再展示计入记忆生成后的开销；两屏使用同一批 24 题，均为总量降幅，不是逐题降幅的算术平均。
